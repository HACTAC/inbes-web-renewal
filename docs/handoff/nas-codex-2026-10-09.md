# INBES Webリニューアル 引き継ぎ

## 1. 結論と最初に行うこと

リニューアルサイトは本番公開済みである。次の担当は、ソースを最新状態へ引き継ぎ、NAS環境の既存Infisical接続を使用して安全な差分公開の運用を整える。サイトの新規制作や旧サイトへの再移行から始める必要はない。

1. GitHubから指定ブランチを取得する。
2. 同梱のソースZIPを別ディレクトリに展開し、GitHubとの差分を確認して取り込む。
3. AGENTS.mdと採用標準を読み、ビルドと検証を行う。
4. 本番の現状を読取りで確認する。
5. 更新対象、保護対象、バックアップ、復旧方法を固定した差分公開処理を準備する。

アクセス関係はInfisicalで開通済み、という本人の引き継ぎ指示を前提とする。資格の再発行・再設定を開始しない。ただし、NAS側の接続成功や書込み処理の実装・承認を、この資料で検証済みとは扱わない。

## 3. 構成と主要ファイル

- Astro 4 / Tailwind CSS 3による静的サイト。Node.jsは開発・ビルド用であり、本番にNodeサーバーは不要。
- 本番はmixhostの静的ファイルとPHPフォーム。Cloudflareが配信経路にある。
- `src/pages/`: TOP、製品一覧、生産完了品、商品化支援、実績、会社概要、お知らせ、フォームなど。
- `src/data/`: 製品、実績、お知らせ、ナビゲーション等の表示データ。
- `src/components/`、`src/layouts/`: 共通UI・ヘッダー・フォーム・解析タグ。
- `public/assets/`: 掲載画像等。画像修正の最終状態もZIPに含む。
- `design-system/`: INBESの既存デザインルール。見た目を独断で作り直さない。
- `server/contact/`: PHPハンドラー、検証、秘密値のない設定サンプル等。ディレクトリ全体を公開領域へアップロードしてはならない。

製品側と法人側の入口・ナビゲーションは文脈別に分け、フォームの送信処理は共通化している。法人の進め方と取扱分野は商品化支援ページへ統合済み。実績は18事例、会社名非掲載、表記は「対応領域」である。

## 5. 保護する旧ページと公開制御

- `/products/`の一覧入口は新サイト。配下の既存個別商品ページは保持する。
- `/cubele/`、`/bulenu/`は保持する。
- `/products.php`はファイルを即削除せず、外部アクセスを新一覧へ302転送する。旧PHPの内部include依存を壊さない。
- 旧ページから参照されるPHP、画像、CSS、JS、PDFも保持する。
- `.htaccess`は新旧共存のため変更済み。DirectoryIndexは新HTML優先・旧PHPフォールバック。サイト一式を再生成した設定で置き換えない。
- 「新サイトからリンクされない」だけで削除可能とは判定しない。動的include、旧ページ相互リンク、PDF等の依存がある。

従来調査では直接リンク26件から到達した旧ファイル1,015件、静的参照の未解決候補29件、要確認ケース21件が残った。削除候補の確定と旧PHPの安全性確認は別作業である。

## 6. ビルド・検証

Node.js 20は既存GitHub Actionsの設定値である。NASで利用可能な互換Node環境を確認し、lockfileを維持して導入する。

```bash
npm ci
env PUBLIC_SITE_URL=https://inbes.jp PUBLIC_DEPLOY_ENV=production PUBLIC_BASE_PATH=/ PUBLIC_GA_MEASUREMENT_ID=G-5SQ5RBJXCT npm run build
npm run check:links
node scripts/test-analytics.mjs
git diff --check
python3 .agents/tools/validate_repository.py --root .agents --knowledge-only
```

GA測定IDは公開識別子であり資格ではない。確認用ビルドに本番の環境値・計測・実メール接続を流用しない。

```bash
env PUBLIC_SITE_URL=https://hactac.github.io PUBLIC_BASE_PATH=/inbes-web-renewal/ PUBLIC_DEPLOY_ENV=review npm run build
env PUBLIC_BASE_PATH=/inbes-web-renewal/ npm run check:links
```

標準Validatorには`.agents/requirements-dev.txt`の依存が必要。macOSではPyYAML不足で未実行だった。NASで導入する場合は隔離した環境を使用し、既存の共用Pythonを無断変更しない。

## 7. 公開方法とNASへの移管

これまでの本番反映は、ログイン済みmixhost/cPanelのFile Managerで行った。非公開領域へ限定ZIPをHTTPSアップロードし、ダウンロードしてSHA256を照合、承認済み公開ルートへ展開、公開内容を読み戻した。継続更新では操作回数が多いため、差分公開の自動化を次の担当へ引き継ぐ。

既存スクリプトの注意点:

- `scripts/prepare-production-migration.mjs`: 初回の旧サイト移行用。既存パスとの衝突を停止する設計であり、更新用としてそのまま再実行しない。
- `scripts/prepare-news-release.py`、`prepare-analytics-release.py`: macOS上の過去リリース保存先を前提とする限定処理。NASへ無変更で実行しない。
- `scripts/prepare-contact-settings.py`: macOS専用readerの絶対パスを参照。既存NAS接続経路へレビュー付きで適合させる必要がある。
- `scripts/verify-live-release.py`: 公開静的ファイルの厳密な照合。CloudflareがHTMLへ追加するbeaconを正規化しないため、HTMLの照合失敗を即座に配置差異と断定しない。既知タグ以外まで除去する緩い比較にしない。
- `scripts/test-live-contact.py`: 実メールを発生させる可能性がある。単なる動作確認として実行しない。

NASの差分公開処理に必要な条件:

1. 開通済みのサイト専用接続経路を使い、資格を標準出力・Git・任意CLI引数へ渡さない。
2. 実際の公開ルート・接続先binding・TLS条件を確認する。macOSのIdentityやbootstrapをコピーして流用しない。
3. 本番現状を取得し、対象ファイルの旧SHA・サイズと新生成物を比較する。
4. 追加・置換・保持・削除をファイル単位で区別し、allowlistと復旧用退避を作る。
5. 旧商品ページ、非公開設定、`.htaccess`、PHP等を通常の静的更新から除外する。
6. 独立レビューと今回の対象に対する直前承認を得てから、限定書込みを行う。
7. 読み戻し照合、通常URLでの表示、主要導線を検証して記録する。

ZIPで1980年の既定更新日時を持つファイルを展開した際、通常URLが旧HTMLを返したことがある。原因は確定していない。最新のお知らせ候補は適切な更新日時を使用するv3へ変更した。転送成功だけで公開完了とせず、キャッシュを含む通常URLの応答を確認する。

## 9. フォーム・解析の残確認

- 管理者通知はPHPMailer 7.1.1、SMTPを使用。送信設定は公開領域外にあり、Gitには保存していない。
- 自動返信は本番有効化済み。実際の送信者受信箱への到着は未確認。本人指定のテスト宛先と直前の実送信承認を確認してから試験する。
- 秘密設定・状態ファイルは0600、専用ディレクトリは0700。公開PHPに秘密を埋め込まない。
- GA4は基本page_view、拡張計測無効。query/hashを解析URLから除外し、フォーム値を計測しない。
- Search Consoleはサイトマップ送信受付済みだが「サイトマップを読み込めませんでした」の表示が残った。TOPのGoogle公開URLテストは登録可能だった。取得成功・新規インデックス登録を完了と扱わない。
- DNS、防御設定、メール設定を推測で変更して解消を試みない。
